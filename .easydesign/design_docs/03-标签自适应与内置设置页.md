# 03-标签自适应与内置设置页设计

## 设计目标

在保留系统原生菜单栏的前提下，再补上一层更接近 Chrome 的高频交互：

1. 去掉最上方的系统标题栏显示，减少“外面还有一层壳”的感觉。
2. 让应用菜单入口更容易点中。
3. 让顶部按钮成为统一的一套视觉系统。
4. 让标签栏在多标签场景下保持紧凑、连续、可读。
5. 让设置等浏览器内置能力开始进入标签页承载模型。

## 窗口壳层设计

### 标题栏策略

- 主窗口保留原生菜单栏，但隐藏系统标题栏显示。
- 目标是去掉截图中最上面那条独立标题区域，只保留浏览器自己的顶部壳层。
- 这样既能保持 Linux / Windows 的原生菜单行为，又不会再看到“窗口标题 + 菜单栏 + 浏览器壳”三层叠加。

### 预期结果

- 用户视觉上直接从菜单栏进入标签区，不再被最顶层标题栏打断。
- 页面顶部整体高度更紧凑，更接近浏览器产品而不是通用系统窗口。

## 按钮视觉设计

### 统一原则

- 顶部所有交互按钮共享同一套基础样式：圆角、边框、暗色渐变、悬浮反馈、按下位移。
- 一级动作（如“打开”）在统一基线上叠加蓝色强调色。
- 次级动作（后退、前进、刷新、菜单、加号）使用同一暗色体系，避免“东一个西一个”。

### 组件分层

1. **次级按钮层**
	- 后退 / 前进 / 刷新 / 新建标签 / 菜单
	- 使用统一暗色按钮样式
2. **一级按钮层**
	- “打开”按钮
	- 保留统一尺寸与圆角，但使用蓝色主操作强调
3. **地址栏容器层**
	- 保持胶囊形输入区
	- 焦点态与主色保持一致，形成一套完整语义

## 标签栏设计

### 布局原则

- 标签轨道与 `+` 按钮属于同一连续视觉区域。
- `+` 按钮固定在“最后一个可见标签之后”，而不是贴死容器最右边。
- 可见标签数量由当前窗口宽度与保留控件宽度共同决定。

### 标签宽度策略

定义三档规则：

1. **宽松区**：标签数量少时，标签使用舒适宽度。
2. **收缩区**：标签增多后，所有可见标签等比压缩。
3. **隐藏区**：标签压到最小宽度仍放不下时，仅显示一个连续可见窗口，其余标签暂时隐藏。

### 最小可见信息

每个可见标签至少保留：

- 加载/站点状态点
- 截断后的标题
- 关闭按钮

其中关闭按钮始终保留，标题不足空间时再让文本收缩。

## 应用菜单入口设计

### 原则

- 系统原生菜单栏继续保留，承担操作系统级菜单与快捷键定义。
- 壳层新增一个更大的应用菜单按钮，承担高频点击入口。
- 菜单按钮样式与导航按钮保持同一套基线，不再像独立拼接的控件。

### 交互

- 渲染层点击应用菜单按钮
- 通过 IPC 把按钮坐标发送给主进程
- 主进程使用原生 `Menu.popup()` 弹出菜单

这样既保留原生菜单能力，也补足点击面积问题。

## 内置页面设计

### 路由策略

先支持一个 Chrome 风格内部地址：

- `chrome://settings`

主进程负责识别该地址，并直接渲染本地内置 HTML，而不是交给外部网络加载。

### 页面结构

设置页分三块：

1. 顶部标题与简介
2. 浏览器壳行为设置
3. 运行时/快捷键说明

### 首版设置项

首版不追求真正可持久化的所有配置，而是优先建立正确的信息架构：

- 启动页说明
- 标签行为说明
- DevTools 快捷键说明
- GPU / 平台策略说明
- 后续可扩展设置项的占位区

## 数据与状态

- 主进程维持真实 tab 列表与活动 tab。
- 渲染层只负责根据当前状态和可用空间，决定哪些 tab 需要展示。
- 内置页面的“地址”仍写入 tab.url，统一显示为 `chrome://settings`。
- 内置页面标题由主进程直接设定为“设置”。

## 验证重点

1. 最上方系统标题栏是否不再显示
2. 顶部按钮是否形成统一的视觉风格
3. 菜单按钮是否足够大且位置顺手
4. 多标签时 `+` 按钮是否始终跟在最后一个可见标签后
5. 标签压缩、截断、隐藏规则是否稳定
6. `chrome://settings` 是否能在标签页中正常打开
7. 页面切换、关闭、激活后状态是否正确
