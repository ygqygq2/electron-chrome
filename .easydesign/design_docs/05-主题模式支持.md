# 05-主题模式支持设计

## 目标

在不重写现有浏览器壳交互的前提下，为 `electron-chrome` 增加三段式主题支持：

- `light`
- `dark`
- `system`

核心目标不是只改几组颜色，而是建立一条稳定的主题状态链路：**主进程决定主题来源，渲染层消费解析结果，菜单与内置页共享同一主题语义。**

## 状态设计

### 主题来源

定义 `themeSource`：

- `light`：强制浅色
- `dark`：强制深色
- `system`：跟随系统

### 解析结果

定义 `resolvedTheme`：

- `light`
- `dark`

当 `themeSource = system` 时，由 Electron 的原生主题能力计算实际明暗。

## 主进程设计

### 数据持久化

- 在用户目录中新增主题偏好文件
- 应用启动时读取偏好
- 主题变化后立即写回

### 原生主题集成

- 使用 Electron `nativeTheme.themeSource`
- 使用 `nativeTheme.shouldUseDarkColors` 计算解析结果
- 监听原生主题更新事件，在 `system` 模式下刷新所有窗口状态

### 状态下发

把下列信息纳入 shell state：

- `theme.source`
- `theme.resolved`

这样渲染层不用自己猜系统主题，避免逻辑分裂。

## 渲染层设计

### 样式策略

继续采用 CSS token，但将 token 分为：

- 默认浅色 token
- `html[data-theme="dark"]` 下的深色 token 覆盖

渲染层只根据主进程下发的 `resolvedTheme` 设置：

- `document.documentElement.dataset.theme`
- 可选：`document.documentElement.dataset.themeSource`

### 视觉要求

#### Light

- 保持当前浅色浏览器风为主基线
- 地址栏、标签、按钮层级清楚
- 页面背景与顶部衔接自然

#### Dark

- 回到更沉稳的暗色浏览器壳，但避免过重的 demo 感
- 地址栏与激活标签保持足够对比
- 状态信息和图标不能发灰到不可读

## 菜单设计

在菜单中加入“主题”子菜单：

- 跟随系统
- 浅色
- 深色

表现形式使用单选项，能明确看到当前选择。

## 内置设置页设计

`chrome://settings` 不再写死深色。

### 方案

- 内置页 HTML 生成函数接收当前解析主题
- 用同一套主题语义渲染浅色 / 深色版本
- 页面可展示当前主题来源和当前生效主题，帮助调试

## 一致性原则

- 同一时刻，顶部壳层与设置页必须属于同一主题语义
- `system` 只是“来源”，最终仍以 `resolvedTheme` 渲染
- 主题切换优先改状态和 token，不改既有交互逻辑

## 风险与规避

### 风险 1：系统主题变化时 renderer 不刷新

处理：由主进程监听原生主题变化并重新广播 state。

### 风险 2：设置页主题与壳层不同步

处理：主题切换后刷新已打开的内部设置页内容。

### 风险 3：深色模式下可读性下降

处理：将深色 token 单独校准，而不是简单反相。

## 验证重点

1. 三种主题来源是否可切换且持久化
2. `system` 模式下系统明暗切换是否有效
3. 顶部壳层深浅模式是否都可读
4. 设置页是否与当前主题一致
5. 菜单状态是否正确显示当前选择
